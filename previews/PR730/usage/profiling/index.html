Profiling

To find out where a GPU application spends its time, use oneAPI.jl's integrated profiler, or an external profiler such as Intel's unitrace or VTune.

For simple timing measurements, see Benchmarking in the Performance Guide.

Integrated profiler

oneAPI.@profile runs code and reports the Level Zero API calls the host made, and the kernels, memory copies and fills that executed on the GPU. It uses Intel's Profiling Tools Interfaces for GPU (PTI), so it also covers work submitted by libraries such as oneMKL. Run the code once beforehand, so that compilation does not end up in the profile:

julia> a = oneArray(rand(Float32, 1024, 1024)); b = similar(a);

julia> c = a * a; copyto!(b, c);   # warm up

julia> oneAPI.@profile begin
           c = a * a
           copyto!(b, c)
       end

With trace=true, the profiler lists every API call and GPU operation in chronological order instead. Their ID column links each GPU operation to the API call that submitted it. To profile code that runs quickly, oneAPI.@bprofile runs it repeatedly for a second (or time seconds) and reports the aggregated results.

The integrated profiler is only available on x86_64 Linux.

oneAPI.@profile — Macro
oneAPI.@profile [trace=false] [raw=false] code...
oneAPI.@profile external=true code...

Profile the GPU execution of code.

There are two modes of operation, depending on whether external is true or false. The default value depends on whether Julia is being run under an external profiler.

Integrated profiler (external=false, the default)

oneAPI.jl collects the activity of code using Intel's Profiling Tools Interfaces for GPU (PTI), and displays two tables:

  • Host-side activity: the Level Zero API calls made while running code, by oneAPI.jl and by libraries such as oneMKL, grouped by function and sorted by time.
  • Device-side activity: the kernels, memory copies and fills that executed on the GPU, grouped by name.

To display a chronological trace instead, set trace to true. The ID column then links API calls to the GPU operations they submitted. Calls that poll for the completion of GPU work are hidden when the work was not done yet, unless raw is set to true.

Slow entries are highlighted: yellow is among the slowest 25%, red among the slowest 5%.

Work submitted to the calling task's stream is synchronized before and after code, so the profile covers its execution. The profile can also contain work from other tasks. GPU operations may overlap in time, so the device-side percentages are relative to the wall-clock time of code, not to the sum of the durations.

External profilers (external=true, when an external profiler is detected)

For more advanced profiling, use an external profiler such as Intel's unitrace or VTune. When started in paused mode (e.g. unitrace --start-paused), wrapping code in oneAPI.@profile external=true restricts collection to that code, using the Instrumentation and Tracing Technology (ITT) API. Work submitted to the calling task's stream is synchronized before resuming the profiler and after code, so that it is attributed to the right side of the boundary; work on other streams or devices is not waited for. When no profiler is attached, code still runs, and a warning is shown.

See the profiling page of the documentation for how to launch Julia under an external profiler.

source
oneAPI.@bprofile — Macro
oneAPI.@bprofile [time=1.0] [trace=false] [raw=false] code...

Benchmark the GPU execution of code by running it repeatedly for time seconds, and report the aggregated results using the integrated profiler (oneAPI.@profile). code runs once before profiling, to exclude compilation, and the task's stream is synchronized after every iteration.

The time keyword argument is optional and defaults to 1.0 seconds; the remaining keyword arguments are forwarded to oneAPI.@profile.

External profilers

External profilers offer more detail, such as hardware metrics. Profiling a whole Julia session also captures compilation and other warm-up work, so to only collect a region of interest, start the profiler paused and wrap that region in oneAPI.@profile external=true:

using oneAPI

a = oneArray(rand(Float32, 1024, 1024))
a * a                           # warm up, not profiled

oneAPI.@profile external=true begin
    for i in 1:10
        a * a
    end
end

When Julia runs under an external profiler, oneAPI.@profile defaults to external=true.

Launching the profiler

oneAPI.jl uses the Level Zero loader and the Intel GPU driver from its own artifacts. An external profiler that loads into the process before Julia starts may pick up another copy of these libraries, e.g., one installed on the system, and then traces that copy instead of the one oneAPI.jl uses. In that case the profile lacks the work oneAPI.jl submits, and oneMKL operations may fail, while oneAPI.@profile warns about multiple loaded copies.

To avoid this, point the loader at oneAPI.jl's copies before launching the profiler. Run the following in the shell you start the profiler from, using the same project as the application. Setting these variables from within the profiled Julia process is too late.

eval "$(julia --project -e '
    using oneAPI
    L0 = oneAPI.oneL0
    loader_dir = dirname(L0.oneAPI_Level_Zero_Loader_jll.libze_loader)
    ld_path = join([loader_dir; split(get(ENV, "LD_LIBRARY_PATH", ""), ":"; keepempty=false)], ":")
    println("export LD_LIBRARY_PATH=", Base.shell_escape_posixly(ld_path))
    println("export ZE_ENABLE_ALT_DRIVERS=", Base.shell_escape_posixly(L0.NEO_jll.libze_intel_gpu))')"

This is not needed when oneAPI.jl is configured to use the system libraries (see Using System Libraries (Advanced)).

unitrace

unitrace is part of Intel's PTI-GPU tools. Start it with --start-paused so that only the code in oneAPI.@profile external=true is collected:

unitrace --start-paused --device-timing --chrome-kernel-logging \
    julia --project workload.jl

--device-timing prints a summary of kernel and memory copy times when the application exits; the Chrome trace can be opened in Perfetto.

VTune

VTune finds the ITT collector through the INTEL_LIBITTNOTIFY64 environment variable, which it sets for applications it launches. Start the collection paused:

vtune -collect gpu-offload -start-paused -- julia --project workload.jl

When attaching VTune to a running Julia process instead, INTEL_LIBITTNOTIFY64 must have been set to VTune's libittnotify_collector.so before Julia started.
